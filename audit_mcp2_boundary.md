# MCP2 boundary audit

- MCPServer constructor allocates per-instance SDK server and all mutable managers; lines 286-404. It also installs TaskStoreAdapter and McpLogTransport (425-438), oninitialized/log forwarding closure (449-480), bridges (481-482), snapshot scheduler + restore async (486-534), eventBus notifications bound to this.server (536-557), completion handler (567-593), and registers ~716 tools (595). Constructing per HTTP request would duplicate timers/listeners/workers and overwrite global registries.
- MCPServerContext couples SDK `server: McpServer` with heavy/global state (context.ts 38-54), routing/activation mutable sets and maps (56-92), transport/shutdown state (94-123), extension maps (125-133), and lazy domain instances (145-213). This interface cannot be safely reused as a per-request context without splitting protocol facade from runtime core.
- registerSingleTool binds callbacks closing over the supplied context and invokes `ctx.executeToolWithTracking`; registration writes into `ctx.server` and SDK internals (MCPServer.tools.ts 159-230). Meta tools/prompts/resources likewise register on `ctx.server` and handlers close over ctx (MCPServer.search.ts 296-329; prompts/resources). A modern factory must register against a fresh per-request McpServer but delegate execution to a stable core context.
- Registry `buildHandlerMapFromRegistry` calls each manifest bind(deps) once; deps proxies capture the context (registry/index.ts 223-249; MCPServer constructor 314-369). Domain ensure() functions mutate ctx and handlers retain ctx. `analysis` and `memory` manifests also use module-level globalContext (analysis 12,27-28,54,181-191; memory 28-34,137-139), so concurrent per-request contexts would race and route progress/sampling to the last one.
- Execution obtains session ID from args._meta, AsyncLocalStorage, else null; browser fleet admission uses `sessionId || 'default'` (execution.ts 156-174), then restore/runExclusive and session pools. All missing protocol sessions collapse to `default`; modern stateless requests need explicit request/session identity or isolated context, otherwise cross-client browser state/leases/pools leak.
- closeServer is global teardown: sets shutdownStarted, stops samplers/schedulers, flushes snapshots, clears TTL, shuts HTTP server, taskManager, closes pools/collector, closes ctx.server and ProcessRegistry (transport.ts 320-512). Never call this per modern request; SDK createMcpHandler teardown must only close request-scoped McpServer/transport.
- Existing HTTP transport is sessionful MultiplexedStreamableHttpTransport; per-session onClose cleans fleet leases, browser/workflow/v8/graphql/collector/proxy states and 10 SessionScopedResourcePools (transport.ts 111-177). Legacy route must preserve this; modern stateless route needs separate cleanup policy (likely no session teardown, explicit handle IDs).

## recommendation
Keep one process-level RuntimeCore/MCPServer for heavyweight managers, domain proxies, taskManager, eventBus, and legacy transport. Add a lightweight protocol adapter/context per modern request that owns a fresh McpServer + request transport and delegates tool execution to core with AsyncLocalStorage request metadata. Do not pass core.server into createMcpHandler; do not invoke closeServer from per-request teardown. Initially expose modern endpoint/feature flag and keep `/mcp` legacy. Before enabling concurrent modern requests, remove module globals or pass request context explicitly for analysis/memory progress and sampling; require explicit session/handle IDs for stateful browser/frida resources instead of default fallback.

## rollout

The first migration slice is available at `POST /mcp/v2` when HTTP transport is enabled. It is a strict modern-only endpoint (`legacy: 'reject'`); existing clients continue using the sessionful `POST /mcp` route. The v2 handler is created lazily on the first request and closed with the process-level server, while each exchange receives a fresh SDK `McpServer`.
